# 《纠结擂台》工程约束与功能规格

> 读者：Claude Code 及所有负责独立实现的前端工程人员  
> 文档目的：定义完整功能、状态、数据依赖和不可越过的产品边界。  
> 本文只规定“必须发生什么”和“绝对不能发生什么”，不规定代码组织、算法、样式写法或技术框架。

---

## 2.1 不可协商的游戏规则

### 完整流程

用户输入问题和双方理由  
→ 系统解释语句并生成两名角色  
→ 用户查看双方能力与技能  
→ 六回合自动战斗逐步展开  
→ 系统公布唯一胜者  
→ 用户选择“接受判决”或“我不服”  
→ 系统保留原判或直接改判  
→ 系统解释用户的反应  
→ 用户保存、分享战报或再来一场

### 规则与优先级

- 🔒 **硬规则：输入必须包含当前纠结的问题、选项 A、选择 A 的理由、选项 B、选择 B 的理由。** 缺少必要信息时不能开始生成。
- 🔒 **硬规则：产品只服务低风险日常选择。** 页面必须清楚但克制地提示，它不用于医疗、投资、法律、学业去留或其他重大决定。
- 🔒 **硬规则：双方角色的名字、能力和技能必须由用户语句派生。** 随机只能制造变化，不能取代语义关联。
- 🔒 **硬规则：相同的完整输入必须形成同一局。** 再次使用完全相同的输入时，角色数据、六回合事件和系统胜者必须一致。
- 🔒 **硬规则：战斗固定为六回合。** 每一回合结束后才公开该回合的战报，不能在开场提前列出全部内容。
- 🔒 **硬规则：能力更有说服力的一方应更可能获胜，但不能保证获胜。** 战斗必须同时体现理由的力量和现实中的意外。
- 🔒 **硬规则：战斗播放与战斗结果必须分离。** 跳过动画只能加快展示，不能重新生成或改变本局结果。
- 🔒 **硬规则：系统公布胜者后，必须同时给出“接受判决”和“我不服”。** 两个选择都要立即生效且只能结算一次。
- 🔒 **硬规则：“我不服”是本产品最核心的产品洞察，不是重赛入口。** 点击后直接让系统败者成为最终胜者，不重新战斗、不重新随机。
- 🔒 **硬规则：结果页必须同时保存“系统原判”和“用户最终选择”。** 改判不能抹掉原判，否则反悔行为失去意义。
- 🔒 **硬规则：首发预填案例是“今晚早睡”与“再刷十分钟手机”，并由后者在最后阶段险胜。** 该结果只服务首次叙事；任意其他输入必须走通用生成与战斗流程。
- 🔒 **硬规则：任意合法的中文日常选项都必须能够完成全流程。** 不能只有首发案例可用。
- 🔒 **硬规则：最终必须有适合手机查看与保存的结果卡。** 结果卡要能独立说明本局冲突、系统胜者、是否改判及偏好结论。
- 🎯 **目标：用户第一次打开页面时，无需阅读长说明就能理解玩法。**
- 🎯 **目标：主要体验紧凑，等待、战斗和结算都不让用户失去上下文。**
- 🎯 **目标：角色反馈既能让用户感到“与我说的话有关”，又有足够娱乐性和可分享性。**
- 🎯 **目标：一局结束后，用户愿意马上测试另一组选择或把战报发给朋友。**

## 2.2 必须处理的状态

以下是用户可感知的状态。实现可以采用任何可靠方式，但不能遗漏状态、混淆状态或留下无法继续的死路。

### 输入状态

用户看到游戏名称、玩法暗示、固定 A/B 形象、预填演示和完整输入表单。用户可以修改任何字段。提交无效内容时，页面应指出需要补充的位置，同时保留已经填写的内容。

**进入方式：** 首次打开、完成一局后选择“再来一场”。  
**离开方式：** 合法提交后进入语句分析状态。

### 语句分析状态

用户看到系统正在读取双方语句、提取特征并构建角色的明确反馈。等待过程应有进展感，不能像页面失去响应。

**进入方式：** 输入提交成功。  
**离开方式：** 双方角色数据准备完成后进入选手确认状态。  
**异常要求：** 重复点击不能启动多套流程；离开该状态后，旧的等待过程不能再次把页面拉回去。

### 选手确认状态

用户看到 A、B 两名角色、原始选项、角色名、五项能力、四个中文技能及简短技能说明。双方都应完整可读，并有清晰入口开始战斗。

**进入方式：** 语句分析完成。  
**离开方式：** 用户确认进入擂台后进入战斗状态。

### 战斗准备状态

用户刚进入擂台，看到问题、双方角色、角色名、满状态血条、回合提示和空的实时战报。此时系统尚未公开任何回合结果。

**进入方式：** 用户从选手确认状态开始战斗。  
**离开方式：** 第一回合开始播放后进入战斗进行状态。

### 战斗进行状态

用户看到当前回合的技能、攻击反馈、生命变化、叙事说明和逐条增加的实时战报。当前问题和双方身份始终可识别。用户可选择跳过展示。

**进入方式：** 第一回合开始。  
**离开方式：** 六个回合均已呈现，或用户选择跳过并立即完成剩余展示。随后进入系统判决状态。

### 系统判决状态

用户看到唯一的系统胜者、胜者对应选项、本局关键结果和两个选择按钮。此时反应计时已经开始，但用户还没有最终表态。

**进入方式：** 本局战斗结果完整确定。  
**离开方式：** 用户首次有效点击“接受判决”或“我不服”。

### 接受结果状态

用户看到系统原判已经生效，系统胜者与最终胜者一致。页面给出轻松的接受文案，不把结果包装成客观真理。

**进入方式：** 用户选择“接受判决”。

### 改判结果状态

用户看到系统原判仍被保留记录，但最终胜者已经直接变为另一方；同时看到反悔用时和与反应速度对应的偏好分析。

**进入方式：** 用户选择“我不服”。

### 分享与保存反馈状态

用户触发保存后，页面要明确反馈结果卡正在生成、已生成或未能生成。失败时不能丢失当前结算内容，用户可以再次尝试。

**进入方式：** 在任一结果状态点击保存战报。  
**离开方式：** 保存完成或关闭反馈后仍停留在当前结果页。

### 重新开始状态

重新开始时要结束上一局尚未完成的动画、计时和反馈，回到可编辑输入页。旧的系统胜者、反应时间和改判结果不能污染新一局。

## 2.3 数据流约束

### 用户直接提供的数据

- 当前纠结的问题。
- 选项 A 与选择 A 的理由。
- 选项 B 与选择 B 的理由。

这些内容是整局唯一的原始依据。显示时必须保留用户语义，不得擅自把选项改写成另一个决定。

### 必须从用户输入派生的数据

- 用于保证本局可复现的局标识。
- 双方角色名。
- 双方五项能力及其语义依据。
- 双方四个技能、技能类型和技能文案。
- 是否属于首发固定演示。
- 六回合的完整事件顺序。
- 每回合的出手方、承受方、使用技能、结果类型、状态变化和战报文案。
- 战斗结束后的系统胜者与结算摘要。

上述派生关系必须让用户输入产生可感知的影响。不能先随机生成结果，再用用户语句为结果补文案。

### 必须保持确定性的数据

在完整输入完全相同的前提下，以下内容必须相同：

- 局标识。
- 角色名、能力、技能及说明。
- 六回合事件顺序与每回合结果。
- 系统胜者。

视觉动画的播放时间、用户何时点击以及设备性能不应改变这些内容。

### 必须记录并传递到后续步骤的数据

- 用户的完整原始输入，用于所有页面回顾与结果卡。
- 已生成的双方角色数据，用于选手页、战斗页和结果页保持一致。
- 已经确定的完整战斗结果，用于逐回合播放、跳过和系统判决。
- 系统原判胜者，结果页无论是否改判都必须保留。
- 判决真正呈现且按钮可操作的时刻，作为反应计时起点。
- 用户首次有效表态的时刻，作为反应计时终点。
- 用户选择的是接受还是不服。
- 用户的最终胜者；接受时等于系统胜者，不服时等于系统败者。
- 是否已经完成结算，防止连续点击产生互相矛盾的结果。
- 结果卡所需的偏好分析文案与展示字段。

### 不得影响核心结果的数据

- 动画是否被跳过。
- 页面滚动位置。
- 用户设备尺寸。
- 保存图片是否成功。
- 用户在战斗播放期间的触摸或点击。

这些数据可以影响展示，但不能改变角色、回合或胜者。

## 2.4 反悔机制的精确语义

> **“我不服”是《纠结擂台》最核心的产品洞察。** 战斗只是制造一个足够具体的外部答案；用户对答案的反应才是产品真正要观察的内容。

### 胜负公布后发生什么

系统必须先结束战斗并明确公布唯一胜者。只有当胜者已经可见、两个选择按钮已经可操作时，才开始记录用户反应。用户此时面对的不是“要不要再抽一次”，而是“我是否愿意接受这个已经发生的结果”。

在用户表态前，系统原判保持稳定，不得因等待时间、动画残留或后台重新计算而变化。

### “接受判决”的逻辑含义

- 用户承认系统原判可以作为这次选择的落点。
- 系统胜者直接成为最终胜者。
- 结果页不显示“本人改判”。
- 产品可以记录用户作出选择所花的时间，但不把它包装成“反悔用时”。
- 文案强调“此刻与直觉站在同一边”，不宣称系统证明了正确答案。

### “我不服”的逻辑含义

- 用户拒绝系统原判，并通过这个动作表达自己更想保护另一方。
- 系统败者立即成为最终胜者。
- 系统原判仍要保留并显示，形成“系统选了什么 / 用户最后救回了什么”的完整故事。
- 不增加确认弹窗，不要求用户再解释理由；第一反应本身就是证词。
- 点击只能生效一次，不能因连续点击在两方之间来回改判。

### 反应计时语义

- **开始：** 系统判决完整呈现，且“接受判决”和“我不服”都已能够操作的瞬间。
- **结束：** 用户首次有效选择其中一个按钮的瞬间。
- 页面切换、动画收尾或保存战报不能继续累加这段时间。
- 计时用于描述用户反应的迅速程度，不用于评价用户性格、理性程度或决定质量。

### 反悔速度对应的文案层次

- **几乎立即反悔：** 强调用户甚至没有犹豫，答案可能早已存在。
- **短暂犹豫后反悔：** 强调用户看过结果、稍作停顿，仍然站到了另一方。
- **思考较久后反悔：** 强调这场外部判决最终让隐藏偏好浮出水面。

三个层次都必须回到同一个核心结论：

> 其实你心里早就有答案。你缺的不是答案，只是一次确认。

文案只解释本次行为，不推断稳定人格，不替用户做重大决定。

### 为什么不能重赛、不能重新随机

“我不服”要捕捉的是用户面对**同一个明确结果**时的反应。如果重新战斗，用户就不再是在表达偏好，而是在反复抽取一个愿意接受的结果；系统也会把一次有意义的反对降格为概率游戏。

直接改判的产品理由是：用户的反对已经成为比原有理由更强的新证词。此时继续让角色战斗是多余的，因为用户已经亲自走进擂台做出了选择。

## 2.5 角色生成规则（语义层面）

### 需要从语句中识别的特征

系统应同时理解选项本身与其理由，至少关注以下语义：

- 是否提到明确的未来时间、截止日期、课程、汇报或必须完成的事项。
- 是否提到睡眠、健康、恢复、疲惫或长期状态。
- 是否表达“现在就能做”“已经在做”“顺手完成”等即时便利。
- 是否出现即时娱乐、短暂承诺、连续观看或“再来一个”的诱惑。
- 是否出现限时、优惠、稀缺、错过就没有等紧迫感。
- 是否描述长期计划、持续积累、已经拖欠或此前投入。
- 是否存在天气、距离、交通、麻烦、花费等外部执行成本。
- 是否会产生明确成果，例如完成工作、做饭、运动或提交任务。
- 是否表达犹豫、懒惰、逃避、不确定或“随便都行”。
- 是否直接表达喜欢、期待、开心、想要、馋或好玩。
- 理由是否具体，是否包含可核对的时间、数量或现实条件。
- 语气是否强烈、迫切、敷衍或自我说服。

### 特征对五项能力的影响方向

- **生命：** 长期收益、恢复价值、持续影响和累积投入会让角色更耐久；纯即时满足、缺乏后续价值会削弱这一方向。
- **攻击：** 明确欲望、强烈情绪、截止压力和稀缺感会让角色更主动、更有冲击力；含糊或缺乏意愿会削弱这一方向。
- **防御：** 具体事实、明确条件、现实后果和充分理由会让角色更站得住；借口、自相矛盾和明显犹豫会让防线变薄。
- **速度：** 已经在进行、立即可做、启动成本低会让角色更容易先行动；距离、费用、天气、麻烦和准备成本会拖慢它。
- **变数：** 犹豫、未知环境、冲动和不稳定因素会增加意外翻盘空间；高度确定、按部就班的选择则更稳定但少有奇招。

一个特征可以同时影响多个方向。产品不追求给句子贴唯一标签，而是让用户看见同一句理由的多面性。

### 角色名的生成思路

- 名字应抓住选项最鲜明的行为或气质，把它变成一个有职位感、物种感或行动感的绰号。
- 常见日常冲突可以有稳定且高质量的命名，例如“早睡执行官”“十分钟诱惑体”。
- 不熟悉的选项也必须得到可读名字，不能显示空白、乱码、无意义编号或生硬截断的整句。
- 名字要有娱乐性，但不能嘲讽用户、贬低某一选项或把选项定性为道德上的好坏。
- 双方名字应有相近的戏剧分量，不能一方非常具体，另一方只是“选项 B”。

### 技能的生成思路

- 每个角色必须拥有四个中文技能，让不同语义有机会在战斗中被看见。
- 技能优先来自用户语句中最有画面的特征，再用与角色气质一致的通用能力补足。
- 技能名是对原句的戏剧化转译，不是把原句机械截取后加上“攻击”。
- 技能说明要短、清楚、有梗，并让用户理解它为何属于这个角色。
- 同一角色的技能应包含不同作用倾向，例如推进、恢复、意外重击或避开压力，避免四个技能只是同义换词。
- 不同输入可以命中相似的语义模板，但角色整体反馈不能完全雷同；用户措辞的差异必须在名字、能力、技能组合或战斗表现中留下痕迹。

### 首发案例的语义要求

- “明天八点有课”和“总是睡不够”应让早睡角色体现未来压力、恢复价值和站得住的理由。
- “视频马上看完”“现在还不太困”和“再刷十分钟”应让刷手机角色体现即时便利、连续诱惑和时间失控的变数。
- 双方都必须显得有逻辑；系统不能把早睡写成绝对正确，也不能把刷手机写成纯粹反派。

## 2.6 战斗规则（目标层面）

### 战斗目标

战斗要把语句差异变成可观看的偏好拉扯：能力更有说服力的一方更可能胜出，但意外始终存在。用户应感觉结果“有依据但不是注定”，从而既愿意相信这局，又有空间产生真实反对。

战斗不能承担“证明正确答案”的责任。它的真正作用是制造一个具体、不可含糊的外部选择，帮助用户观察自己的反应。

### 为什么是六回合

六回合足以形成一段完整的小故事：双方登场、各自表达理由、中段出现反转、最后形成胜负；同时又足够短，不会把一个日常纠结拖成复杂策略游戏。

节奏应满足：

- 开场尽快让双方都表达一次核心理由，用户能认出角色与自己的输入有关。
- 中段要出现状态变化或叙事转折，让用户开始暗中站队。
- 后段要放大紧张感，但不能靠突然修改规则制造假悬念。
- 最后一回合要完整可见，并自然连接到胜负公布，不能被裁切、跳过或埋在日志之外。
- 战报必须与回合同步逐条增加，让用户在当下读取因果，而不是提前看到结局。

### 战斗事件的叙事含义

- **普通伤害：** 一条理由暂时削弱了另一条理由的说服力。
- **暴击：** 某个欲望、压力或现实后果突然击中用户的要害，短时间内分量大增。
- **闪避：** 另一方靠环境、借口或不确定性绕开了本轮说服，但不能让事件完全失去反馈。
- **治疗：** 用户想起此前忽略的长期价值、已经付出的成本或真实需求，让一个动摇的选择重新站稳。

事件文案应优先解释“为什么发生”，而不是只报告抽象伤害。

### 双方参与感

- 双方都必须在战斗中拥有清晰的出手机会和至少一次值得记住的事件。
- 不能出现一方从开场到结束始终沉默、只承担伤害的局面。
- 强弱差距可以影响局势，但不能让较弱方失去角色存在感。
- 连续行动可以作为技能或剧情高潮，但不能让整局像单方面播放胜者动画。
- 即使最终差距明显，用户仍应能说出双方各自为什么有机会赢。

### 首发演示的战斗要求

首发案例必须让“十分钟诱惑体”在最后阶段险胜。战斗叙事要呈现：早睡一方拥有扎实、长期、有恢复力的理由；刷手机一方依靠立即可做、连续推荐和时间悄悄流失完成反超。

“险胜”是重点。它既复刻现实中的深夜失守，也为用户快速点击“我不服”创造最自然的情感条件。

## 2.7 移动端体验约束

### 单手完成的关键操作

- 用户在竖屏手持手机时，应能轻松完成字段切换、提交生成、进入擂台、跳过动画、接受判决、点击“我不服”、保存战报和重新开始。
- 主要按钮不能被系统底部区域、键盘或页面边缘遮挡。
- 结束输入后，用户不应为了找到下一步而进行长距离回滚。
- 关键按钮必须有足够明确的触摸反馈，防止用户不知道是否点击成功。

### 擂台上的空间关系

- A、B 分别属于擂台左、右两个等宽区域，并围绕中线形成明确镜像关系。
- 两个角色主体到中线的视觉距离应相等；B 不能比 A 更靠近中间。
- 双方尺寸、视觉重量和登场高度应平衡，即使轮廓、耳朵或天线不同，也不能造成一方显得被挤压。
- 双方应面向彼此，中线和 `VS` 清楚表达冲突，但不能遮挡角色。
- 角色位置在攻击、受击和恢复后应回到稳定位置，不能越打越偏。

### 任意支持宽度下都不能被裁切的内容

- 角色主体，以及耳朵、天线、手臂、阴影和 A/B 徽章。
- 双方角色名、生命状态和血条的关键信息。
- 当前问题和回合进度。
- 技能提示、伤害反馈和当回合战报。
- 完整六回合战报，尤其是最后一回合。
- “接受判决”和“我不服”两个核心按钮。
- 结果页中的系统胜者、本人改判、反悔用时和偏好分析。
- 结果卡中的长选项文字与保存入口。

### 竖屏信息密度

- 每个状态都应优先展示完成当前任务所需的信息，避免装饰性大空白。
- 文字不能为了塞进一屏而缩小到难以阅读；应通过层级与取舍保持紧凑。
- 战斗期间，问题、角色、反馈和战报应形成一个连续故事，不能迫使用户在多个区域来回滚动才能理解同一回合。
- 桌面浏览时可以呈现居中的手机体验，但桌面适配不能破坏手机优先的版式关系。

## 2.8 工程边界

### 绝对不做

- 不调用外部大语言模型接口，也不要求用户提供任何 API 密钥。
- 不依赖后端服务、数据库或远程计算才能完成核心流程。
- 不做登录、注册、账号体系或跨设备同步。
- 不做排行榜、联机对战、用户社区、评论区或好友关系。
- 不做角色养成、道具、复杂策略构筑或长期数值成长。
- 不做付费、广告、订阅或虚拟货币。
- 不接入微信、抖音或其他平台专属能力。
- 不进行复杂 AI 绘图；角色是固定的抽象载体，不根据输入实时生成图片。
- 不把产品扩展到医疗、投资、法律、重大升学就业或其他高风险决策。
- 不收集与核心体验无关的个人信息，也不把输入内容发送到外部服务。
- 不允许外部资源加载失败后阻断输入、战斗、结算或结果保存。

### 必须满足的技术结果

- 这是一个完整可运行的前端工程，而不是静态效果稿或只能演示预填案例的原型。
- 核心体验必须在没有后端、没有外部 API 的情况下独立完成。
- 项目必须能够作为静态网站部署，并能在常见手机浏览器中通过公开链接访问。
- 生成、战斗和结算规则应彼此边界清晰，使未来替换语义生成方式时，不必重新设计战斗和反悔流程。
- 所有用户可见中文必须正常显示，不出现乱码、截断标签或异常字符。
- 用户输入在所有展示位置都必须被安全处理，不能被当作页面指令执行。
- 动画、等待和计时在离开对应状态后必须停止，不能干扰下一局。
- 快速点击、重复提交、跳过动画和连续返回都不能产生多个胜者、重复结算或状态倒退。
- 核心功能不能依赖特定开发工具才能运行；交付物必须包含清楚的启动、检查、构建和部署说明。
- 实现技术栈不作硬性指定。Claude Code 可以根据项目规模自行选择，但不得让框架复杂度压过游戏本身，也不得改变本文件定义的产品行为。

### 完成前必须验证的用户结果

- 首发预填案例可以从输入完整走到保存战报，并按叙事要求由 B 险胜。
- 更换为任意合理的日常中文描述后，仍能生成与语句有关的角色并完成六回合。
- 相同输入重复运行时，系统原判保持一致。
- 跳过动画与完整观看得到同一个系统胜者。
- “我不服”只改判、不重赛，结果页保留系统原判并展示用户最终选择。
- 三种反悔速度层次都能得到符合语义的文案。
- 窄竖屏下 B 不靠近中线，双方角色及附属造型不被裁切。
- 六回合战报逐条出现且全部可见。
- 保存的结果卡能独立读懂，不依赖返回游戏页面解释。
